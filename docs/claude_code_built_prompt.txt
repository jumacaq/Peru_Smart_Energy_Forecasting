## 0. Ground rules for the build

- Use `uv` for all environment/dependency management. Do not use `pip` directly or `venv`.
- Target Python 3.11 on Ubuntu 24.04.
- Every module in `src/` must be importable and unit-testable in isolation — no
  notebook-only logic. Notebooks only call into `src/`.
- All timestamps are timezone-naive local Peru time (`America/Lima`, UTC-5, no DST).
  Do not silently localize/convert; assume the raw data is already in local time and
  validate that assumption in `data_loader.py`.
- Every model wrapper must implement the same three methods so they're interchangeable
  in the benchmarking loop: `fit(y_train, X_train=None)`, `predict(horizon, X_future=None)`,
  and `save(path)` / `load(path)`. This is the most important architectural constraint —
  don't let any individual model's quirks leak into the benchmarking code.

## 3. `src/data_loader.py`

Responsibilities:

```python
def load_raw_data(path: str) -> pd.DataFrame: ...
def parse_and_index(df: pd.DataFrame, date_col: str = "DATE") -> pd.DataFrame: ...
def enforce_30min_grid(df: pd.DataFrame) -> pd.DataFrame: ...
def validate_series(df: pd.DataFrame) -> dict: ...
def load_processed_dataset(path: str = "data/processed/demand.parquet") -> pd.DataFrame: ...
```

Requirements:
- `parse_and_index`: parse `DATE` to `datetime64[ns]`, set as `DatetimeIndex` named
  `DATE`, sort ascending, drop exact duplicate timestamps.
- `enforce_30min_grid`: `reindex` against `pd.date_range(start, end, freq="30min")` so
  every one of the 35,040 expected slots exists. Missing `Demand` values after reindex
  should be interpolated with **time-based linear interpolation** for gaps ≤ 4 steps
  (2 hours) and flagged (not silently filled) for longer gaps — log a warning listing
  the gap ranges.
- `validate_series`: return a dict report with row count, expected vs actual count,
  number of missing timestamps, number of duplicate timestamps, min/max demand,
  min/max date, and count of non-positive or NaN values. Raise if `Demand` has negative
  values (physically invalid for load).
- Persist the cleaned dataframe to `data/processed/demand.parquet` (parquet, not CSV —
  preserves dtypes and is faster to reload for repeated benchmarking).

## 4. `src/feature_engineering.py`

All 30-minute steps. Build a single function `build_features(df, target_col="Demand")`
that returns a feature matrix + target, plus smaller composable helpers so individual
model wrappers can pick a subset (e.g., GBDT wants lags + calendar; Prophet wants none
of this — it wants a plain `ds`/`y` frame; statistical models want none of this either).

```python
LAGS = [1, 2, 48, 336]          # 30min, 1h, 1 day, 7 days
ROLLING_WINDOWS = [48, 336]     # 1 day, 7 days

def add_lag_features(df, target_col, lags=LAGS) -> pd.DataFrame: ...
def add_rolling_features(df, target_col, windows=ROLLING_WINDOWS,
                          stats=("mean", "std", "min", "max")) -> pd.DataFrame: ...
def add_calendar_features(df) -> pd.DataFrame: ...
def add_cyclical_encodings(df) -> pd.DataFrame: ...
def build_features(df, target_col="Demand", dropna=True) -> pd.DataFrame: ...
```

Calendar features to include:
- `hour`, `half_hour_of_day` (0–47 slot index), `day_of_week`, `day_of_month`, `month`,
  `quarter`, `is_weekend`.
- `is_holiday` using Peru's public holiday calendar — use the `holidays` package
  (`uv add holidays`) with `holidays.Peru()`; don't hardcode a holiday list by hand.
- Cyclical encodings (`sin`/`cos`) for `hour`, `day_of_week`, `month`, and
  `half_hour_of_day` since these are periodic, not ordinal — this matters more for GBDTs
  and the LSTM than for Prophet, which has its own seasonality terms.
- Rolling features must use `.shift(1)` before rolling so no row leaks its own current
  value into its own features (critical — check this carefully, it's the most common
  time-series leakage bug).

## 5. `src/metrics.py`

```python
def mae(y_true, y_pred) -> float: ...
def rmse(y_true, y_pred) -> float: ...
def mape(y_true, y_pred, epsilon=1e-8) -> float: ...
def smape(y_true, y_pred) -> float: ...   # bonus: more stable than MAPE near-zero demand
def evaluate_all(y_true, y_pred) -> dict: ...   # returns {"MAE":..., "RMSE":..., "MAPE":..., "sMAPE":...}
def evaluation_table(results: dict[str, dict]) -> pd.DataFrame: ...  # model name -> metrics dict -> tidy df
```

`evaluate_all` is what every model's benchmarking step calls — keeps the comparison
table construction in `scripts/run_benchmark.py` trivial.

## 6. Model wrappers — common interface (`src/models/base.py`)

Define an abstract base class every wrapper inherits from:

```python
class BaseForecaster(ABC):
    @abstractmethod
    def fit(self, y_train: pd.Series, X_train: pd.DataFrame | None = None) -> "BaseForecaster": ...
    @abstractmethod
    def predict(self, horizon: int, X_future: pd.DataFrame | None = None) -> pd.Series: ...
    @abstractmethod
    def save(self, path: str) -> None: ...
    @classmethod
    @abstractmethod
    def load(cls, path: str) -> "BaseForecaster": ...
```

`horizon` is always expressed in number of 30-minute steps so it's consistent across
models and matches the Streamlit app's slider later.

### 6a. `statistical.py` — Holt-Winters
- Wrap `statsmodels.tsa.holtwinters.ExponentialSmoothing`.
- Seasonal period = 48 (daily seasonality at 30-min resolution) as the primary; note in
  a docstring that a 336-period (weekly) seasonal model is also worth trying but
  triple-seasonal Holt-Winters isn't natively supported — mention `statsmodels`' single
  seasonal limitation and suggest TBATS/`prophet`/GBDT pick up the weekly pattern instead.
- `trend="add"`, `seasonal="add"`, damp trend if series doesn't look strongly trending.

### 6b. `prophet_model.py`
- Convert to Prophet's required `ds`/`y` schema inside the wrapper (don't leak this
  requirement into `data_loader.py`).
- Enable `daily_seasonality=True`, `weekly_seasonality=True`, `yearly_seasonality=True`.
- Add Peru holidays via `Prophet(holidays=...)` built from the same `holidays.Peru()`
  source used in feature engineering, for consistency.
- `predict` builds the future dataframe via `model.make_future_dataframe(periods=horizon, freq="30min")`.

### 6c. `fast_forecast.py`
- Implement only after the API discovery step in Section 1. Keep the wrapper thin —
  translate `fit`/`predict`/`save`/`load` to whatever that library actually exposes.
- If, after inspection, the package turns out not to support arbitrary-horizon 30-min
  forecasting cleanly, note that clearly in a comment and fall back to its closest
  supported mode rather than forcing a mismatch.

### 6d. `GBDT_model.py`
- Use `skforecast.recursive.ForecasterRecursive` (or `ForecasterAutoreg` depending on
  the installed `skforecast` version — check the installed version's API since this
  changed across skforecast releases) wrapping `lightgbm.LGBMRegressor` as the primary
  and `xgboost.XGBRegressor` as an alternate configurable via a constructor arg.
- Feed it `build_features` output as exogenous regressors; lags handled by skforecast's
  own `lags=` parameter using the same `LAGS` list from `feature_engineering.py` (avoid
  defining lag lists twice).
- Use `skforecast.model_selection.backtesting_forecaster` or
  `bayesian_search_forecaster` for a light hyperparameter search over
  `num_leaves`/`learning_rate`/`n_estimators` — keep the search small (this is a
  benchmarking script, not a production tuning pipeline).

### 6e. `lstm_model.py`
- PyTorch (already added). A small sequence-to-one architecture: sliding window of
  past `N` steps (start with `N=336`, one week) → 1–2 LSTM layers (hidden size ~64) →
  linear head → single-step-ahead prediction, then iterate forward autoregressively for
  multi-step horizons (or, better, train it as seq2seq if time permits — mention both
  as options and implement the simpler autoregressive one first).
- Must fit a `StandardScaler` (or `MinMaxScaler`) on the training target only, save it
  alongside the model (`models/lstm_scaler.pkl`), and apply the same transform at
  inference. Un-scale before returning predictions from `predict()`.
- Keep training short by default (configurable `epochs`, default ~20, with early
  stopping on a held-out slice of the training window) — this is a benchmark entry, not
  a tuned production model.

## 7. Benchmarking script — `scripts/run_benchmark.py`

Workflow:
1. Load `data/processed/demand.parquet`.
2. Split: last 1,440 rows (30 days × 48 steps) = test set; everything before = train.
3. For each model in `{HoltWinters, Prophet, FastForecast, GBDT_LightGBM, GBDT_XGBoost, LSTM}`:
   - fit on train
   - predict `len(test)` steps ahead
   - compute `evaluate_all(y_test, y_pred)`
   - time the fit and predict calls too (wall-clock seconds) — worth reporting alongside
     accuracy since some of these models are far slower than others
4. Build a comparison table with `evaluation_table` sorted by RMSE ascending.
5. Print the table, save it to `models/benchmark_results.csv`.
6. Identify the best model by RMSE (configurable to rank by MAE or MAPE instead), refit
   it on the **full** dataset (train + test) so the deployed model uses all available
   history, then serialize:
   - `models/best_forecaster.pkl` — the model itself, via each wrapper's own `save()`
   - `models/best_forecaster_meta.json` — model name, metrics achieved on the held-out
     test set, feature list used, training date range, and horizon step size, so
     `app.py` can display provenance without re-deriving it.

`notebooks/02_benchmark.ipynb` should just import and call this script's functions,
plus add plots (predicted vs actual overlay per model, residual plots) — keep the heavy
logic in the script, not the notebook.

## 8. `app.py` — Streamlit dashboard

- Load `models/best_forecaster_meta.json` to show which model is deployed and its
  benchmark metrics in a sidebar info panel.
- Load the model via its wrapper's `load()` (dispatch on the model name stored in the

- Sidebar controls:
  - Horizon selector: slider or selectbox in **hours** (24h to 168h) that internally
    converts to steps (`hours * 2`) before calling `predict()`.
  - Optional: date picker to choose the forecast origin if historical data allows
    backtesting from an arbitrary point, not just "now".
- Main panel:
  - Plotly line chart: recent actual demand (e.g., last 7 days) + forecast continuing
    from it, with a visually distinct style/color for the forecast segment.
  - An interactive/sortable table of the forecasted timestamps and values below the
    chart (`st.dataframe`), with a CSV download button (`st.download_button`).
- Cache data/model loading with `st.cache_resource` / `st.cache_data` so switching the
  horizon slider doesn't reload the model from disk every rerun.
